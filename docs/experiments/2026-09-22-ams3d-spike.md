# Spike: AMS3D tree crown segmentation on the Berlin 2021 ALS tiles (2026-09-22)

**Question.** Can we segment individual tree crowns from the freshly downloaded
Berlin ALS point clouds (`/Volumes/2TB/winmol/ALS_Data/berlin_als_2021`, flight
Feb/Mar 2021, leaf-off, ~20 pts/m², classified) with adaptive mean shift 3D
(AMS3D, Ferraz et al. 2012/2016), and how does that compare to the crown file we
already have for R13 (`ALS segmentation 2017.gpkg`, 538k crowns, R13 only)?

**Answer.** Yes, a plain numpy/scipy AMS3D works and yields sensible crowns on
both a Tegeler Forst (R12) and a Spandau (R13) hectare. Out of the box it
over-segments tall crowns vertically; merging converged modes generously
(1.5 m horizontal / 6 m vertical, clusters < 50 points absorbed) fixes that and
lands at roughly the reference tree density. Agreement with the reference file
is moderate (about 52 % of reference crowns get a matching AMS3D apex, 63 % of
AMS3D apexes fall in a reference crown), but the reference is itself an
unvalidated segmentation product, not ground truth. Runtime of this
implementation is 5 min/ha, so the full R12 (515 ha) would take ~2 days on a
laptop; that is the real blocker, not quality.

## What was run

`ams3d_spike.py` (throwaway). Steps: load one 1 km tile, cut a 100 m × 100 m
patch (+10 m buffer), height-normalise with a 1 m ground grid from class-2
points, keep vegetation points 2–60 m above ground, run mean shift from every
point with a cylinder kernel whose radius and half-height grow with the current
height (h_s = 0.12·h, h_r = 0.27·h, ratios read off the reference crowns:
mean diameter / height and mean crown length / height), union modes closer than
a merge tolerance, export convex-hull crowns + apex points to GeoPackage and
plot CHM / clusters / cross-section.

Patches: `r12` = 381300–381400 E, 5828300–5828400 N (tile 381/5828, inside the
R12 footprint), `r13` = 376400–376500 E, 5827400–5827500 N (tile 376/5827,
covered by the reference crowns).

Matching rule for the R13 comparison: an AMS3D apex counts as a match if it
lies inside a reference polygon and the heights differ by ≤ 3 m; one match per
reference crown.

## Results on the R13 hectare (407 reference crowns)

| config | change vs default | trees/ha | matched | recall | precision | mean diam [m] | height RMSE [m] |
|---|---|---|---|---|---|---|---|
| default | h_r = 0.27·h, merge 1 / 2 m, min 20 pts | 798 | 289 | 0.71 | 0.36 | 5.3 | 0.79 |
| A | h_r = 0.5·h, merge z 4 m | 518 | 227 | 0.56 | 0.44 | 5.6 | 1.02 |
| B | A + h_s = 0.15·h, min 50 pts | 290 | 180 | 0.44 | 0.62 | 7.8 | 0.84 |
| C | default kernel, merge 1.5 / 6 m, min 50 pts | 339 | 213 | 0.52 | 0.63 | 7.9 | 0.76 |

Reference: 407 crowns/ha, mean diameter 5.8 m, mean height 22.8 m.

The R12 hectare (no reference) gives 658 trees/ha with the default config and
a visibly more open pine canopy; see `ams3d_spike_r12.png`.

Figures: `ams3d_spike_r13.png` (default), `ams3d_spike_r13_C.png` (config C),

## Observations

- **Vertical splitting is the main failure mode** of the textbook kernel on
  leaf-off data: a point 12 m up a 30 m pine gets a 3 m vertical window and
  converges to a mode inside the lower crown, so tall trees come out as 2–3
  stacked clusters (cross-section in `ams3d_spike_r13.png`). Widening the
  vertical bandwidth (A, B) helps less than merging modes afterwards (C), and
  costs 2–3× more runtime because the neighbour sets grow.
- **Config C matches the reference's crown count and height distribution**
  (339 vs 407/ha, height RMSE 0.76 m on matches) but its crowns are larger
  (7.9 vs 5.8 m): it also absorbs the understorey stems that the reference keeps
  as separate 6–10 m trees, which explains most of the missed recall.
- **Convergence**: a few percent of seeds oscillate at the hard cylinder edge
  and never drop below the 5–10 cm tolerance, so every run hits the 40-iteration
  cap; harmless, the active set is tiny by then.
- **Runtime**: 2–4 min/ha for the default kernel, 5–10 min/ha for the wider
  ones, on 170–260k vegetation points. This is pure numpy + cKDTree; a compiled
  implementation would be needed for the 515 ha R12 footprint.

## Recommendation

AMS3D on these tiles is feasible and gives crowns of the same character as the
existing R13 file, so it is a credible way to get crowns for R12, where the
reference file has none. Before spending on it: (1) decide what the crowns are
for (windthrow susceptibility per tree vs stand structure), because a
CHM-based watershed / local-maxima segmentation would give comparable canopy
crowns at a fraction of the cost, and AMS3D only earns its keep if the
understorey layer matters; (2) if going ahead, use a compiled tool rather than
this script, and calibrate the merge tolerances against a hand-checked plot
rather than against the R13 file.
